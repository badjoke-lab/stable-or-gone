# Stable or Gone post-351 data-growth operating specification

Status: canonical operating specification  
Updated: 2026-07-10  
Activation: after PR #351 merges

## 1. Purpose

This specification governs Stable or Gone after completion of the current public-surface expansion sequence.

The repository now has the required public research surfaces:

```text
Registry record pages
Stats
Compare
Compare presets
Access & Regulation Explorer
Change Timeline
Update Feed
Maintenance Log
machine-readable projections and manifest discovery
```

The default operating mode now changes from surface expansion to reviewed data growth and maintenance.

## 2. Product-surface freeze

New public pages, explorers, dashboards, ranking surfaces, or major navigation families are not the default next work.

A new public-surface PR chain requires:

1. a specific user or research need;
2. evidence that existing surfaces cannot answer it;
3. a reviewed roadmap amendment;
4. a canonical specification before implementation;
5. an explicit preservation plan for existing routes, machine outputs, and data semantics.

Small maintenance, accessibility, readability, broken-link, and correctness fixes remain allowed.

## 3. Post-351 operating lanes

Work proceeds through five coordinated lanes.

### 3.1 Data depth and record growth

Purpose: deepen reviewed canonical records and expand the registry only through evidence-backed audited changes.

Primary targets:

```text
identity and lineage
organization relationships
lifecycle history
reserve and backing structure
issuance and redemption
legal profiles
regulatory notes
deployments
events
evidence relations
known unknowns
comparison-critical coverage
facet freshness support
```

### 3.2 Canonical Market Access promotion

Purpose: convert only reviewed, bounded, evidence-backed access claims into canonical Market Access Records under PR #341 governance.

Approved flow:

```text
research or monitoring signal
-> duplicate and scope review
-> source confirmation
-> evidence relation
-> bounded claim drafting
-> manual canonical review
-> reviewed repository PR
-> merge
-> public canonical projection
```

Monitoring observations, editorial matrices, guides, platform licences, and generic platform availability claims are not canonical Market Access Records by themselves.

### 3.3 Monitoring review

Purpose: use read-only monitoring to reduce discovery cost while preserving the private review boundary.

Monitoring may:

```text
observe
compare
classify
identify stale review state
prepare private review material
discover bounded leads
```

Monitoring may not:

```text
write canonical data
self-accept baselines
publish candidates
publish monitoring rows
create canonical PRs automatically
edit guides automatically
deploy
```

### 3.4 Corrections and evidence maintenance

Purpose: maintain existing records, not only add new ones.

Work includes:

```text
broken-link repair
archive supplementation
official-source replacement
evidence relation correction
record wording correction
date correction
organization relationship correction
known-unknown resolution
source identity maintenance
```

### 3.5 Monthly maintenance

Purpose: maintain a public-safe operational checkpoint without exposing private research material.

The monthly cycle remains:

```text
new month -> in_progress
month activity -> public-safe aggregate updates
month-end review -> close month
closed month -> immutable
next month -> append new entry
```

## 5. Record Depth & Coverage Baseline

PR #353 must measure the current 110-asset registry before deepening begins.

The baseline must evaluate at least:

```text
identity
lifecycle
organization relationships
mechanism and classification
reserve structure
redemption
issuance
deployment
legal profile
regulatory notes
events
evidence depth
known unknowns
comparison readiness
facet freshness support
canonical market access coverage
```

The baseline is an internal planning instrument, not a public risk score or asset ranking.

Allowed planning states:

```text
strong
usable
partial
sparse
absent
not_applicable
```

The baseline must preserve explicit unknown and not-applicable semantics and must not infer factual values.

## 6. Tier A dossier deepening

Tier A batches deepen important assets before attempting uniform depth across all 110 assets.

Selection must use the PR #353 baseline and product leverage.

Selection considerations include:

```text
market significance
historical importance
failure or migration importance
regional relevance
comparison demand
regulatory relevance
Market Access research potential
current evidence gaps
```

An initial priority pool may include major issuer-backed, protocol-backed, synthetic, regional, failed, migrated, and discontinued assets, but final batch membership is chosen from the baseline rather than hard-coded by this specification.

Each Tier A PR should normally cover no more than five assets unless the roadmap amendment explicitly approves a different bound.

A Tier A batch may add supporting canonical records and evidence but must not add new canonical assets unless the PR explicitly includes an audited growth scope.

## 7. Market Access pilots

Market Access pilots must be bounded.

A pilot defines:

```text
jurisdiction set
asset set
platform or service set
function set
access-state vocabulary
effective-date rules
evidence requirements
review cutoff
```

The pilot must prioritize reliable evidence and reviewability over row count.

No universal allowed/banned boolean is permitted.

Function state remains separate for at least the reviewed functions supported by evidence, such as:

```text
buy
sell
deposit
withdraw
custody
convert
mint
redeem
payment rail
other explicitly specified function
```

A platform licence is not proof that a specific asset/function combination is available.

## 8. Broad record growth

After initial Tier A deepening, broader growth resumes in reviewed batches.

For PRs that add new canonical assets, the existing controlled-growth limit remains:

```text
maximum two new canonical stable assets per growth PR
```

Supporting record groups must be preserved as applicable.

Growth batches should be grouped by research context when practical:

```text
issuer-backed
protocol-backed
synthetic or delta-neutral
regional and non-USD
failed, discontinued, migrated, or rebranded
under-documented long tail
```

## 9. Review gate after PR #360

The review gate must examine:

```text
which record families remain sparse
whether Tier A dossiers materially improved Compare utility
whether Timeline gained useful historical density
whether Access & Regulation gained canonical Market Access utility
which monitoring signals produce actionable reviewed work
correction and source-maintenance burden
monthly maintenance burden
external usage or referral evidence when available
```

The next PR sequence must be chosen from this evidence.

The review gate may authorize more dossier batches, more Market Access pilots, broader record growth, evidence cleanup, or a separately justified product-surface amendment.

## 10. PR traceability and mandatory reference rule

Every post-351 non-trivial PR must cite:

```text
AGENTS.md
docs/spec-governance.md
docs/roadmap.md
docs/post-351-data-growth-operating-spec.md
active roadmap amendment
work-item-specific specification
named baseline, queue, audit, or research checkpoint
```

Before implementation begins, the active work item must be checked against these documents.

A PR that cannot identify its roadmap item and governing specification must pause.

## 11. Data-preservation rules

All post-351 work preserves:

```text
canonical-only public release claims
candidate/private/monitoring separation
unknown-state semantics
source and evidence identity
historical checkpoint immutability
statistics history immutability
Comparison Readiness semantics
facet freshness semantics
Timeline date semantics
Update Feed publication-date semantics
Maintenance Log public-safety boundary
no composite risk score
no asset ranking
no investment recommendation
```

## 12. Operating conclusion

Stable or Gone has completed the current public-surface expansion sequence.

The next competitive advantage must come primarily from:

```text
deeper evidence-backed dossiers
canonical Market Access data
reviewed historical density
stronger evidence maintenance
safer monitoring-assisted research
visible long-term maintenance discipline
```

The repository should not default back to building new UI surfaces merely because a new surface can be built.
